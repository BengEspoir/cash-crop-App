# AgriculNet PWA and app subdomain setup

## Runtime architecture

The installable application is the existing Next.js client. It can be served from both agriculnet.farm and app.agriculnet.farm; no second frontend build is required. The manifest is generated by client/src/app/manifest.js, and client/public/sw.js provides a deliberately narrow offline cache.

The service worker caches immutable Next.js assets, public images, and public navigation. It does not intercept authenticated API, auth, admin, KYC, payment, order, dispute, conversation, backup, restore, password-reset, or verification paths. Listing drafts and explicitly safe profile changes use user-scoped IndexedDB instead of the shared HTTP cache.

## Configure app.agriculnet.farm

1. In Vercel, open the AgriculNet frontend project and add app.agriculnet.farm under Domains.
2. In Cloudflare DNS, create the exact CNAME target Vercel displays for app. Keep the record proxied only after Vercel reports the certificate as valid.
3. Add app.agriculnet.farm to the production Turnstile widget hostname list.
4. Add it to Railway:

       TURNSTILE_ALLOWED_HOSTNAMES=agriculnet.farm,www.agriculnet.farm,app.agriculnet.farm

5. Add https://app.agriculnet.farm to Supabase Authentication URL Configuration as an allowed redirect URL.
6. If the backend CORS policy uses one CLIENT_URL, retain the canonical https://agriculnet.farm; add the app subdomain to the backend allowlist before routing authenticated traffic from that host.

## Install and update behavior

- Browsers that support beforeinstallprompt show a dismissible install suggestion. Dismissal is remembered for seven days.
- iOS users install from Safari's Share menu using Add to Home Screen.
- A newly installed service worker triggers a visible update action; it is not activated silently while a form is open.
- Logout deletes IndexedDB records owned by that user.

## Offline acceptance checks

1. Build and serve the production client over HTTPS.
2. Open a public marketplace page once, then use browser DevTools to go offline and reload it.
3. Open the listing wizard, enter data, reload offline, and confirm the draft returns.
4. Confirm payment, verification, admin, and message requests fail closed while offline and are never queued.
5. Sign out and inspect Application -> IndexedDB to confirm records for that user are removed.
6. Change the server profile from another browser before reconnecting an offline profile draft; the client must report a conflict instead of overwriting newer data.

The app is a progressive enhancement. Browser storage can be cleared by the operating system, so IndexedDB drafts are a resilience aid rather than permanent storage.
